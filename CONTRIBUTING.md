# Contributing to Wattage

All contributions, no matter the size, are welcome. This guide is here to help you get started.

## Reporting Issues

If you found a bug and would like to report it, visit the [issue tracker](https://github.com/v81d/wattage/issues).

You can also make a feature request on the issue tracker.

Please make sure you follow the template correctly. Provide all necessary information. If you don't, it will be harder to identify the bug and hence take longer to solve the issue. Thanks!

Also, please note that not all bugs may be fixed quickly. Some issues may take several weeks or even months depending on maintainer availability and, in general, the severity of the issue. Some issues may also be out of Wattage itself and is more closely related to, for example, a specific Linux distribution or desktop environment. In such cases, the issue may remain open for others to see but unresolved until it is fixed for the distro/DE.

If you would like to help fix an existing bug, you are absolutely welcome to [open a pull request](https://github.com/v81d/wattage/pulls).

## Translating the Project

If you would like to add or update translations, you are absolutely welcome to do so! For more details, see the [Translating Guide](TRANSLATING.md).

## Making Pull Requests

If you would like to submit a patch or feature directly to Wattage, you can submit a pull request. To bring your feature/fix to life:

1. Fork the repository.
2. Create a feature branch (`git checkout -b feature/my-feature`) or a fix branch (`git checkout -b fix/my-fix`).
3. Commit your changes (`git commit -m "feat: add new feature"`). **Please follow the [Conventional Commits](https://www.conventionalcommits.org) guideline when doing so!**
4. Push the branch (`git push origin feature/my-feature`).
5. Open a pull request with `main` as the base branch. Make sure to create a detailed title and description of your change.

Please follow the [GitHub flow](https://guides.github.com/introduction/flow) and the [GNOME Code of Conduct](https://github.com/v81d/wattage/blob/main/CODE_OF_CONDUCT.md) along with the guidelines below when submitting a pull request.

### Contributor Guidelines

Everyone is welcome to contribute to Wattage. However, in order to keep things organized, contributors must follow these rules:

- **Use conventional commits and branches.** This is more of a style guideline than an actual rule, but contributors are HIGHLY encouraged to use these conventions when naming commits and branches. Doing so will make clear the intent of each piece of your work. For example, if your commit is for a bugfix, you might name it something like `fix: remove endless loop causing memory leak`. On the other hand, if your commit is a simple code enhancement or optimization, you could title it something like `refactor: use guard clauses in display_dialog() function`. Of course, these are very basic examples, but if you'd like to see a more detailed guide, you should check out qoomon's [Conventional Commit Cheatsheet](https://gist.github.com/qoomon/5dfcdf8eec66a051ecd85625518cfd13).
- **Be clear.** Please title your pull request in a way that's understandable and not low-effort. Doing this will make it much easier for maintainers to understand what you are trying to merge. For example, instead of titling a pull request "feat: add function," you could say "feat: create show_dialog() function for displaying modals." Also, make sure you have a proper description that accurately describes your proposed changes.
- **Do not infringe on copyright or licenses.** If you think it is even remotely necessary to credit or acknowledge someone in a part of your code, please do it.
- **Link related issues or PRs.** Pretty self-explanatory. This just makes the pull request easier to categorize and, more generally, makes it easier to track as time passes.
- **If your code contains AI-generated or AI-assisted portions, review it fully.** Refer to the section below for more details.

### AI Policy

Truthfully, we don't think it would do the FOSS community any good if we were to outright ban all contributions that use AI, even ones that genuinely fix something important.

If your code contains AI-generated or AI-assisted portions, **review it from top to bottom**! _You_, not the agent, will be held responsible for the entirety of your contribution, so please make sure you do not miss out on any potentially important details.

That said, all contributions who fall under this category must follow these guidelines:

- **Carelessly vibe-coded contributions will not be accepted.** A human must be involved in a meaningful way. Vibe coding tends to produces slop code, and slop is low-quality. By all means, you can use AI to _assist_ you in your contribution, but you must use it wisely.
- **No user-facing strings may be generated by AI.** This means that all text visible to the user via terminal output and the graphical interface must be human-written. This is part of the effort to encourage contributors to read AI-produced code rather than blindly committing it. However, it is also to make sure the parts of the app that are visible to the user remain high-quality.
- **Review all AI-generated code.** Whenever you use AI-generated code, review it from top to bottom. And twice. Make sure you understand the code and catch any potential bugs before you commit!

Changes to these guidelines may be made as more contributions are received, but we hope this turns out to be helpful to all contributors.

A warm thank you to all contributors for making the FOSS community a better place. And as always, happy coding. :)
